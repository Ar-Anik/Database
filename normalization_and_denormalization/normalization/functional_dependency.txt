Q : What is a Functional Dependency (FD)?
-> A functional dependency (FD) is a rule that says:
If we know the value of some attribute(s) X, then we can determine the value of some other attribute(s) Y.
We write it as: X → Y (read: X determines Y)

# Example of FD
Imagine we have a table STUDENT:
| Student_ID | Name    | Department | Email                                      |
| ----------- | ------- | ---------- | ----------------------------------------- |
| 101         | Alice   | CSE        | [alice@uni.edu](mailto:alice@uni.edu)     |
| 102         | Bob     | EEE        | [bob@uni.edu](mailto:bob@uni.edu)         |
| 103         | Charlie | CSE        | [charlie@uni.edu](mailto:charlie@uni.edu) |
----------------------------------------------------------------------------------

-> Suppose t1 and t2 are two rows in the table.
If t1[X] = t2[X], then necessarily t1[Y] = t2[Y].
Example with Student_ID → Name:
    * Row1: Student_ID=101, Name=Alice
    * Row2: Student_ID=101, Name=?
If both rows have the same Student_ID (101), then they must have the same Name (Alice). If they don’t, the FD
is violated.

-> Candidate Keys and FDs
A candidate key is an attribute (or set of attributes) that uniquely identifies a row.
If X is a candidate key of relation R, then: X → everything in R. Example:

In STUDENT, Student_ID is a candidate key. So: Student_ID → Name, Department, Email

# Important Notes
If X → Y, it does not mean that Y → X. Example:
Student_ID → Name
But not Name → Student_ID because two students might have same name.

Q : Why need functional dependencies?
-> Functional dependencies are constraints that help:
    1. Validate data correctness
    2. Design good database schemas (normalization)
    3. Avoid redundancy & anomalies
