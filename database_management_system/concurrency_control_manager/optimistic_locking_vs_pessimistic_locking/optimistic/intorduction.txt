Optimistic Locking হলো computer system-এ ব্যবহৃত একটি concurrency control mechanism, বিশেষ করে database-এ। এটি shared
resources access manage করতে ব্যবহৃত হয়। এটি এই ধারণার উপর base করে কাজ করে যে, data ব্যবহারের সময় একাধিক user/process-এর
মধ্যে conflict হওয়ার সম্ভাবনা খুবই কম।

-> Key Concepts of Optimistic Locking
1. Validation Before Commit:
একই সময়ে একাধিক user-কে data c করতে বাধা দেওয়ার পরিবর্তে, Optimistic Locking conflict যাচাই করার কাজটি data commit করার সময়
পর্যন্ত স্থগিত রাখে। এটি প্রতিটি transaction-কে কোনো ধরনের বাধা ছাড়াই স্বাধীনভাবে কাজ করার সুযোগ দেয়। এই পদ্ধতিটি এমন একটি ধারণার উপর ভিত্তি করে
কাজ করে যে, data নিয়ে কাজ করার সময় সাধারণত transaction গুলোর মধ্যে কোনো conflict তৈরি হবে না।

2. Validation at Commit Time):
Access ডেটার change গুলো save/commit করার আগে, system data validation করে। এটি পরীক্ষা করে দেখে, বর্তমান transaction শুরু হওয়ার পর
থেকে অন্য কোনো transaction একই data ইতোমধ্যে পরিবর্তন করেছে কি না। এই validation সাধারণত ডেটার সাথে যুক্ত version number বা timestamp
মিলিয়ে করা হয়।
যদি version বা timestamp পরিবর্তিত পাওয়া যায়, তাহলে বোঝা যায় যে অন্য কেউ data-টি update করেছে অর্থাৎ একটি conflict ঘটেছে।

3. Handling Conflicts:
validation ধাপে যদি কোনো conflict ধরা পড়ে অর্থাৎ বর্তমান transaction চলাকালীন অন্য কোনো transaction একই data পরিবর্তন করে থাকে তাহলে
system প্রয়োজন অনুযায়ী ব্যবস্থা নেয়। এই ক্ষেত্রে বর্তমান transaction-টি rollback করা হতে পারে। অথবা last updated data নিয়ে পুরো change-টি
আবার retry করার জন্য নির্দেশ দেওয়া হতে পারে।


-> Advantages
1. Reduced contention: এটি কোনো resource-কে block না করেই একাধিক process-কে কাজ করার অনুমতি দেয়, যা সামগ্রিকভাবে system-এর গতি
বা concurrency বৃদ্ধি করে।

2. Minimal locking overhead: এখানে transaction-গুলো স্বাধীনভাবে সম্পন্ন হয়, যার ফলে বারবার lock করা বা lock manage করার বাড়তি ঝামেলা
ও সময় ব্যয় কমে যায়।


-> Disadvantages
1. Increased chances of conflicts: যদি একই সময়ে অনেক user একই data নিয়ে কাজ করে, তবে বারবার transaction পুনরায় শুরু করতে হতে
পারে। এর ফলে অতিরিক্ত logic check এবং কাজের জটিলতা বেড়ে যায়।

2. Not suitable for highly contended resources: যেসব ক্ষেত্রে ঘনঘন conflict হওয়ার সম্ভাবনা থাকে, সেখানে Optimistic Locking খুব একটা
efficient approach নয়।


-> Use of Optimistic Lock
1. Low Contention
যেসকল system-এ একই সময়ে একই ডেটা নিয়ে একাধিক user কাজ করার বা data পরিবর্তনের সম্ভাবনা অনেক কম থাকে, সেখানে Optimistic Locking Most
Effective। বিশেষ করে Read-heavy system এবং Non-critical data অপারেশনের ক্ষেত্রে এটি সবথেকে ভালো ফল দেয়। এটি কোনো blocking ছাড়াই
Concurrent Access নিশ্চিত করে, যার ফলে একাধিক user একসাথে কাজ করতে পারে এবং system-এর overall speed increases।

2. Short Transactions
যখন একটি transaction অত্যন্ত fast বা স্বল্প সময়ের মধ্যে সম্পন্ন হয়, তখন মাঝপথে অন্য কেউ এসে data update করার বা conflict তৈরি করার ঝুঁকি
অনেক কমে যায়। Optimistic Locking-এর non-blocking প্রকৃতির কারণে এটি ব্যবহারের ফলে অহেতুক অপেক্ষার প্রয়োজন হয় না। এতে system-এর
Response time fast হয় এবং মেমোরি বা storage রিসোর্সের সঠিক ব্যবহার নিশ্চিত হয়। এটি মূলত একটি logic check এবং validation মেকানিজম
ব্যবহার করে কাজ শেষ করে।

3. Scalability
যদি কোনো project অনেক বেশি user থাকে এবং ডেটাবেস লকিংয়ের(Pessimistic Locking) কারণে Performance কমে যাওয়ার বা ডেডলক হওয়ার আশঙ্কা
থাকে, তবে সেখানে Optimistic Locking ব্যবহার করা বুদ্ধিমানের কাজ। এটি ডাটাবেস engine-এর ওপর অতিরিক্ত চাপ সৃষ্টি না করে কেবল write করার সময়
version check করে। এর ফলে সিস্টেমটি অনেক বেশি ইউজারের চাপ নিতে সক্ষম হয়।

4. Distributed Systems
আধুনিক মাইক্রোসার্ভিস বা ডিস্ট্রিবিউটেড আর্কিটেকচারে যেখানে অনেক সময় নেটওয়ার্ক ল্যাটেন্সি থাকে, সেখানে দীর্ঘক্ষণ কানেকশন ধরে রাখা বা লক করে রাখা ঝুঁকিপূর্ণ। এই পরিস্থিতিতে Optimistic Locking একটি নির্দিষ্ট sequence মেনে কাজ করে এবং ডেটার নিখুঁত অখণ্ডতা বজায় রাখে।
