Q: What means Fine-Grained?
--> Fine-Grained means having precise, controlled, and selective control over how and when locks are released,
    rather than following a broad, one-size-fits-all approach.

Q: What means Concurrency and Consistency?
1. Concurrency (Multiple Transactions Running Together)
    * Concurrency refers to how many transactions can execute at the same time without interfering with each other.
    * Higher concurrency means more transactions can proceed simultaneously, leading to better system performance.
    * Lower concurrency occurs when transactions are forced to wait for locks to be released.

    -> High concurrency = More transactions run in parallel = Faster processing

2. Consistency (Ensuring Data is Correct & Predictable)
    * Consistency means transactions maintain the correctness of the database, ensuring that all transactions see valid, up-to-date data.
    * A consistent system prevents dirty reads, lost updates, and other anomalies that could cause incorrect results.

    -> Strong consistency = Data always remains valid and predictable, even if concurrency is lower.


Q: Why Do We Need Lock Release Protocols If We Already Have 2PL Variants?
--> Even though 2PL, Strict 2PL, Rigorous 2PL, and Conservative 2PL define how locks are acquired and released in
    structured ways, lock release protocols provide fine-grained control over when locks are released within those
    broader concurrency control mechanisms.

--> Lock release protocols work within concurrency control protocols like 2PL to fine-tune transaction behavior.
    They allow for better performance optimization, deadlock handling, and trade-offs between consistency and
    concurrency.

--> 2PL Variants control when transactions can acquire or release locks globally, but lock release protocols give
    finer control over release timing. They help improve performance, prevent deadlocks, and adapt to different
    workloads while following 2PL rules.

# Key Reasons for Lock Release Protocols
1. 2PL Variants Focus on Locking Strategy, Not Fine-Grained Release
    * 2PL Variants Define When Locks Can Be Released (e.g., at commit, after use, or based on an order).
    * Lock Release Protocols Define How They Are Released (e.g., immediate, delayed, or at predefined points).
Example:
    * Strict 2PL: Holds all locks until commit. But it does not specify how to release locks after commit (all at once or in stages).
    * Lock Release Protocols: Can help optimize when and in what order locks are released.

2. Performance Optimization in High-Concurrency Systems
    * Strict and Rigorous 2PL reduce concurrency by holding locks longer.
    * Lock release protocols balance concurrency and consistency by defining when to release locks within the constraints of 2PL variants.
Example:
    * Immediate Release in some read-heavy transactions may improve concurrency under basic 2PL.
    * Predefined Release Points can allow selective unlocking of read locks while keeping write locks until commit.

3. Deadlock Prevention & Mitigation
    * Conservative 2PL prevents deadlocks by acquiring all locks at the start, but it doesn’t specify how to release locks efficiently.
    * Lock release protocols can help mitigate deadlocks by defining structured ways to release locks without violating 2PL rules.
Example:
    * Predefined Release Points can release low-priority locks earlier in Conservative 2PL to reduce resource holding time.

4. Adaptability for Different Workloads
    * Some workloads favor high concurrency, while others require strict consistency.
    * Lock release protocols help tailor 2PL implementations to different database transaction needs.
Example:
    * A banking transaction (high consistency) → Uses delayed release under Strict 2PL.
    * A social media feed update (high concurrency) → Uses immediate release under Basic 2PL.


** "Compute" refers to the processing or calculation performed by a transaction between reading and writing data.

Q: What is Lock Release Protocol and Different Type of Lock Release Protocol?
--> Lock release protocols determine when a lock on a data item is released in a database or concurrency control system.

1. Immediate Release
-> Behavior: Locks are released as soon as the operation on the data item is completed.

-> Advantage: Maximizes concurrency by allowing other transactions to access the data item quickly.

-> Disadvantage: Can lead to inconsistent data because another transaction might read partially updated data before
   the transaction is fully completed.

-> Example:
    T1: Lock(X) → Read(X) → Unlock(X) → Compute → Lock(Y) → Read(Y) → Unlock(Y)
* If another transaction modifies X after T1 unlocks it but before T1 finishes computing, T1 may work with
  inconsistent data.

-> Use Case: Generally avoided in transactional systems requiring strong consistency.

2. Delayed Release
-> Behavior: Locks are held until the transaction commits or aborts.

-> Advantage: Ensures data consistency by preventing premature access to uncommitted changes.

-> Disadvantage: Reduces concurrency, as other transactions must wait until the transaction completes.

-> Example:
    T1: Lock(X) → Read(X) → Compute → Lock(Y) → Read(Y) → Compute → Commit → Unlock(X), Unlock(Y)
* X and Y remain locked until T1 completes, preventing other transactions from accessing them.

-> Use Case: Used in strict two-phase locking (Strict 2PL) to ensure serializability and avoid cascading rollbacks.

3. Predefined Release Points
-> Behavior: Locks are released at specific points in the transaction code, typically based on predefined logic.

-> Advantage: Balances concurrency and consistency by allowing partial release while maintaining essential locks.

-> Disadvantage: Requires careful planning to prevent issues like deadlocks or inconsistencies.

-> Example:
    * T1: Lock(X) → Read(X) → Compute → Unlock(X) → Lock(Y) → Read(Y) → Compute → Unlock(Y)
* Locks are released in a structured manner, ensuring that dependent operations complete before unlocking

-> Use Case: Used in optimistic concurrency control or hybrid locking strategies where fine-grained control over locks is needed.
